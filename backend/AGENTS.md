# AGENTS.md - Backend

## Overview

Express 5 REST API with Prisma 7 ORM, SQLite database, JWT authentication, and i18n support.

## Development Workflow

Before committing any change:

1. Create a branch from `develop`: `<type>/<task id>-<slug>` for a plan task (`fix/`, `feature/`, `chore/`, `docs/`, see `docs/plan/README.md`), `feature/xxx` or `fix/xxx` otherwise
2. **Add or update tests** for any new or modified feature (see Testing section below)
3. Ensure TypeScript compiles: `npm run typecheck` (`tsc --noEmit` on `src/`, then `tsconfig.config.json` for `vitest.config.ts` and `prisma.config.ts`, which `npm run build` keeps out of `dist/`)
4. Ensure lint and build pass: `npm run lint` (config in `eslint.config.js`), `npm run build`
5. Run tests: `npm test`
6. **Verify coverage thresholds are met**: `npm test -- --coverage`
7. Commit, push, open PR to `develop`

CI runs automatically on PRs (`Backend` job of `.github/workflows/ci.yml`): `npm ci` (prisma generate) → `npm audit --omit=dev --audit-level=high` → `npm run db:check` → `npm run typecheck` → lint → build → tests with coverage → delta coverage (80%). The `Docker build (backend)` job builds the image, and the `Smoke` workflow starts it with the frontend (see the root `AGENTS.md`).

## Testing Requirements

**Every new feature or bug fix MUST include integration tests.** A PR will not pass CI until:

1. **Tests are written** covering all new/modified routes, services, and utilities
2. **All tests pass**: `npm test`
3. **Global coverage thresholds are met** (60% minimum):
   - Statements >= 60%, Branches >= 60%, Functions >= 60%, Lines >= 60%
4. **Delta coverage on PRs** (80% minimum): at least 80% of new/modified lines must be covered

### Test conventions

- Test files live next to their source: `routes/bottles.test.ts`, `services/availabilityService.test.ts`
- Use the shared helpers from `src/test/helpers.ts` (DB lifecycle, auth, seed factories). Build test data with the factories (`seedFullCocktail`, `seedMenu`, `seedMenuSection`, `addCocktailToMenu`, `addBottleToMenu`, `seedBottle`…) rather than `prisma.*.create`, and extend them when a test needs more
- Each test file follows: `setupTestDatabase()` in `beforeAll`, `cleanDatabase() + seedRequiredData()` in `beforeEach`, `teardownTestDatabase()` in `afterAll`
- Tests run against a real SQLite test DB (`prisma/test/test.db`, defined in `src/test/testDatabase.ts` only), not mocks. It has a folder of its own, so that the copies a restore keeps in `backups/` never mix with those of the developer database in `prisma/backups/`. `src/test/globalSetup.ts` empties and creates this folder once per run and deletes it entirely at the end; `cleanDatabase()` empties every table of the schema
- The test database is shared by every test file of a run: a test that alters the schema (trigger, index, extra table) must restore it in `finally` (or `afterEach`/`afterAll`)
- Run with coverage locally: `npm test -- --coverage`
- `vitest.config.ts` pins the reporter, so the console of passing tests shows the same under an AI agent as in a terminal or in CI (Vitest would otherwise pick its `minimal` reporter under an agent)

## Key Patterns

### Route Pattern

Handlers never catch errors to answer them. Express 5 forwards rejected promises to
`errorHandler` (`src/middleware/errorHandler.ts`), which maps them to `{ error, details? }`:

```typescript
import { Router } from 'express';
import { prisma } from '../lib/prisma';
import { NotFoundError } from '../errors';
import { valid, validate } from '../validation/validate';
import { idRequest } from '../validation/common';

const router = Router();

// Never create a PrismaClient: import the shared one from src/lib/prisma.ts
router.get('/:id', validate(idRequest), async (_req, res) => {
  const item = await prisma.model.findUnique({
    where: { id: valid<typeof idRequest>(res).params.id },
  });
  if (!item) throw new NotFoundError();
  res.json(item);
});

export default router;
```

- Throw the classes of `src/errors.ts` (`BadRequestError`, `NotFoundError`, `ConflictError`, `ForbiddenError`…) with an i18n key.
- Let Prisma errors propagate: the middleware maps P2025 to 404, P2002 to 409, P2003 to 409 on DELETE (400 otherwise) and Prisma validation errors to 400.
- Keep a local handler only for callbacks outside the handler's promise (stream `error` events, multer `destination`): Express never sees those errors.

### Auth Pattern

- Middleware in `auth.ts` extends `Request` as `AuthRequest` with `userId?: number`
- Public routes: `/api/auth/login`, `/api/public/*`, `/api/health` (mounted before the rate limiter, answers status and version only) and the photos under `/uploads` (no middleware)
- Protected routes: all others (authMiddleware applied in `app.ts`, or in `routes/auth.ts` for `/me` and `/logout-all`)
- JWT token in `Authorization: Bearer <token>` header, HS256, 7-day expiry by default (`JWT_EXPIRES_IN`)
- Tokens are issued by `signToken()` and checked by `verifyToken()` (`middleware/auth.ts`) only. A token carries
  `User.tokenVersion` (`tv`): changing the password or `POST /api/auth/logout-all` increments it, which revokes every
  older token. A token of a deleted user is refused too. Restoring a backup made with v1.11.0 or later raises the
  restored version above both the backup's and the live one (`backupService.ts`), so every session ends, the restoring
  one included. A backup made before v1.11.0 has no column: the restore writes the live version to
  `<database>.session-floor`, and the next start applies it after the migrations (`services/sessionFloor.ts`, C-30)
- `POST /api/auth/login` allows `LOGIN_RATE_LIMIT` failed attempts (default 10) per client IP in 15 minutes, then
  answers 429. Every `/api` route except `/api/health` allows `API_RATE_LIMIT` requests (default 600) per client IP
  in one minute, counted before the body parsers and `authMiddleware`; `/api/backup` also allows 10 authenticated
  requests in 15 minutes, counted after `authMiddleware`. Build a limiter with `createRateLimiter()`
  (`middleware/rateLimit.ts`), never `rateLimit()` directly; tests that send many requests to a strict limiter call
  `resetRateLimits()` in `beforeEach`. Clients that share an address share the counters; an IPv6 client counts
  for its /64 network (`ipv6Subnet: 64` in the factory, C-51). `trust proxy`
  (`TRUST_PROXY`) trusts the proxies on loopback and private networks by default: the
  client IP is the last public address forwarded by nginx and any reverse proxy in front of it. A successful login
  rehashes a password hash made at another cost (`needsRehash`)
- One password rule (`src/bootstrap/password.ts`): `hashPassword()` (bcrypt cost 12) and `MIN_PASSWORD_LENGTH` (12),
  used by `ensureAdmin` and `PUT /api/settings/profile`. Never call `bcrypt.hash` elsewhere
- CORS is closed by default (same-origin app); `CORS_ORIGIN` allows one origin

### Input Validation (zod)

Every route that reads `params`, `query` or `body` declares zod schemas and runs `validate(...)`
(`src/validation/validate.ts`). An invalid request ends in a 400 whose `details[]` lists
`{ path, code, message }` (e.g. `path: 'body.ingredients.0.bottleId'`). The handler reads the parsed,
typed values with `valid(res)`, never `req.params`, `req.query` or `req.body` directly:

```typescript
const updateSchemas = { params: IdParams, body: UnitUpdate };

router.put('/:id', validate(updateSchemas), async (_req, res) => {
  const {
    params: { id },
    body,
  } = valid<typeof updateSchemas>(res);
});
```

- One schema file per resource in `src/validation/`, shared building blocks in `common.ts`
  (`IdParams`, `Percent`, `RequiredText`, `Translations`...). Schemas never import Prisma: they
  describe the HTTP contract, which the frontend types come from (see below).
- `z.object` drops unknown keys: the schema is the whitelist of what a request can write.
- Path and query values are strings: coerce them (`z.coerce.number()`). JSON bodies are not coerced.
- `req.query` is a getter in Express 5 and cannot be assigned: read it through `valid(res)`.
- One deliberate exception: `routes/public.ts` reads `req.params` itself. An invalid cocktail id
  answers **404**, not 400, so a guest learns nothing about which ids exist (task A-05); the menu
  slug is only used as a lookup key.

### Response contracts and frontend types (F-05)

- A response schema sits next to the request schemas of its resource (`Bottle`, `Cocktail`,
  `Unit`...); those of `routes/public.ts` are in `validation/public.ts`. They are strict
  (`z.strictObject`): a field a route adds, drops or retypes fails the contract tests. Dates are
  `Timestamp` (ISO strings, as JSON sends them), stored translations `StoredTranslations`.
- `src/routes/responseContracts.test.ts` parses the answer of each covered route with its schema.
  A route that gets a response schema gets a test there.
- `src/contracts/frontendTypes.ts` lists what the frontend gets: `z.output` of the response
  schemas, `z.input` of the request bodies, and the constants of the unions (`SOURCE_TYPES`,
  `MENU_TYPES`). `npm run contracts:generate` writes `frontend/src/types/generated.ts` from it, as
  the TypeScript compiler infers each type. `generateFrontendTypes.test.ts` fails while that file
  is out of date: after a schema change, run the script and commit both.
- The frontend never imports zod schemas from here: it validates its forms with its own rules.

### Translations

Entity names support multi-language via JSON strings stored in SQLite (`'{"fr": "Rhum", "en": "Rum"}'`).
Never `JSON.stringify` or `JSON.parse` them by hand: use the helpers of `src/utils/translations.ts`:

- `serializeTranslations(body.nameTranslations)` writes the value the `Translations` schema checked
  (`undefined` leaves the column untouched, blank languages are left out, nothing left clears it);
- `parseNameTranslations(entity)` turns the strings of an entity and of its relations into objects
  before `res.json()`: every response sends objects, never strings;
- `parseTranslations(raw)` reads one column (exports).

The names and translations of categories, units and ingredients, and the translations of category
types, go through `nameToStore` / `translationsToStore` (`src/utils/storedNames.ts`) before they are
written: a new value is stored composed (NFC), a value sent back exactly as stored is kept.

### File Uploads

Every upload goes through multer, whose `limits.fileSize` is the largest file accepted, that size included: multer (2.5.0) passes `fileSize + 1` to busboy, which stops as soon as a file reaches the limit it is given. A file of exactly the limit is therefore accepted, one byte more gives `LIMIT_FILE_SIZE` and a 413. One exported constant per limit, used by multer and by the tests at the boundary (limit - 1, limit, limit + 1):

| Upload         | Constant                                                 |
| -------------- | -------------------------------------------------------- |
| Cocktail photo | `MAX_IMAGE_BYTES` (`services/cocktail/cocktailImage.ts`) |
| Bottle import  | `MAX_BOTTLE_IMPORT_BYTES` (`utils/bottlesImport.ts`)     |
| Backup restore | `MAX_BACKUP_UPLOAD_BYTES` (`services/backupService.ts`)  |

nginx (`frontend/nginx.conf.template`) limits the whole multipart body, so its `client_max_body_size` keeps a margin above each limit for the multipart envelope. `src/uploadLimits.test.ts` reads the template and fails when a file of exactly a backend limit, with its envelope, would no longer fit under the limit of its nginx location. The admin page checks the backup size before sending it (`frontend/src/pages/admin/SettingsPage.tsx`).

### Image Upload

- Limit: `MAX_IMAGE_BYTES` (see File Uploads)
- Accepted: jpg, jpeg, png, webp. multer keeps the file in memory; sharp (`services/cocktail/imageVariants.ts`) decodes it once (`MAX_INPUT_PIXELS`, 100 Mpx, bounds the memory), applies the EXIF orientation, drops every metadata block (GPS included) and writes `<uuid>.webp` (1600 px wide at most, the name stored in `imagePath`), `<uuid>-960.webp`, `<uuid>-480.webp` and `<uuid>-og.jpg` (1200 px, the `og:image` of link previews). The upload itself is never kept (decision of 2026-11-27); a file sharp cannot read, or one over the pixel limit, gets a 400 (`errors.invalidImage`)
- Every copy is named after `imagePath` (`derivedVariantNames()`), with no schema change: `frontend/src/utils/uploads.ts` builds the same names. Deleting or replacing a photo deletes its copies
- Photos stored before the copies existed keep their original file, never rewritten. `backfillImageVariants()` adds the missing copies in the background at startup (`src/index.ts`) and after a backup restore; until then the public pages and link previews use the photo itself
- Stored at the root of `config.uploadDir`: `UPLOAD_DIR`, or `<repo>/uploads` when it is not set. The Docker image and both compose files set `UPLOAD_DIR=/app/uploads` (the `uploads` volume)
- Served statically at `/uploads/*`
- Tests build real images with `src/test/images.ts` (`testImage()`, `jpegOfSize()`, `writeStoredPhoto()`)

## Dependencies

**Runtime**: express 5, express-rate-limit, bcryptjs, cors, helmet, morgan, jsonwebtoken, multer, sharp (photo copies; libvips prebuilt in its optional `@img/sharp-<platform>` packages, no install script), archiver and adm-zip (backups), i18next, i18next-http-middleware, dotenv, zod 4, yaml (front matter of the release notes)
**Runtime (database)**: @prisma/client 7, @prisma/adapter-better-sqlite3 7, better-sqlite3 12 (native module, prebuilt for linux x64/arm64 musl), prisma 7 (the CLI applies the migrations when the container starts)
**Dev**: typescript 5.9, tsx, eslint 10, typescript-eslint, prettier 3, vitest, supertest

**Install scripts**: npm 12 skips the install scripts of dependencies that `allowScripts` in `package.json` does not list (npm 11.19 only warns). Only `better-sqlite3` is allowed: without its script the native binary is missing. `esbuild`, `prisma`, `@prisma/engines` and `fsevents` are denied (`false`): their binaries come from platform packages or from `prisma generate` (the project `postinstall`). Keys have no version, so a Dependabot bump keeps working. A new dependency whose script is needed must be added to `allowScripts` (`npm install-scripts approve <pkg> --no-allow-scripts-pin`), otherwise denied (`npm install-scripts deny <pkg>`), so that `npm ci` prints no `install-scripts` warning. The `prod-deps` stage of the `Dockerfile` opens `better-sqlite3` and encodes an image with `sharp`, and fails the build when either binary is missing. It prunes with `--omit=dev` only: `--omit=optional` would drop the binary of sharp, so the optional peers of the dev tooling (typescript, magicast) are cut by `docker/prune-unused-deps.mjs` instead.

The Docker image holds the runtime dependencies only and runs as the `node` user (uid 1000): code that runs there (server, seed, scripts) lives in `src/` and is compiled by `npm run build`. It never relies on `tsx`. The image has no `src/`: the Dockerfile bundles `prisma.config.ts` with `src/lib/databasePath.ts` into `dist/lib/prisma.config.js` (esbuild), which `docker/prisma.config.js` loads, so `databasePath.ts` imports Node built-ins only. A new file in `src/scripts/` stays a thin entry point and is added to the coverage exclusions (`vitest.config.ts` and `ci.yml`).

## Database

- SQLite file at `prisma/carta_cocktail.db`. A relative `file:` path in `DATABASE_URL` starts from `prisma/` (`resolveDatabasePath()`, `src/lib/databasePath.ts`), for the application and for the Prisma CLI (`prisma.config.ts`) alike. URL parameters are ignored
- Prisma 7 client (`prisma-client` generator), generated into `src/generated/prisma/` by `npm install` (`postinstall`) or `npx prisma generate`. Import models, `Prisma` and `PrismaClient` types from there, never from `@prisma/client`
- One shared `PrismaClient` (`prisma` in `src/lib/prisma.ts`), also used by the seed, the scripts and the test helpers. Any other client (backup restore, tests on a temporary file) comes from `createPrismaClient(url)`: never call `new PrismaClient` elsewhere
- Queries outside a transaction wait until the open interactive transaction ends, as with Prisma 6 (`src/lib/serializedAdapter.ts`). Inside a `$transaction(async (tx) => …)` callback, use `tx` only: a call to the shared `prisma` would wait for the transaction itself, until it times out
- The client talks to SQLite through `@prisma/adapter-better-sqlite3`: one connection, 5 s busy timeout, `DateTime` stored as Unix milliseconds as Prisma 6 did (`timestampFormat: 'unixepoch-ms'`; ISO strings would sort apart from the existing rows)
- The CLI reads `.env` through `prisma.config.ts`; `src/lib/prisma.ts` loads `backend/.env` itself. `npm run db:check` sets its own `DATABASE_URL` (Prisma 7 needs a datasource to replay the migrations, and silently finds no difference without one)
- WAL journal mode, set at startup; `SQLITE_WAL=false` keeps the rollback journal, required when the database sits on a network share (SMB/NFS)
- Cascading deletes on most relations
- Unique constraints on slugs, name pairs, menu-entity pairs
- Seed creates: 1 admin, 3 category types (SPIRIT/SYRUP/SOFT), 18 units, 2 system menus (aperitifs/digestifs), site settings

## Ingredient Source Types

`CocktailIngredient.sourceType` determines which FK is populated:

- `BOTTLE` → `bottleId` (specific bottle)
- `CATEGORY` → `categoryId` (any bottle from category)
- `INGREDIENT` → `ingredientId` (free ingredient like lime, sugar)

For `CATEGORY` sources, `CocktailPreferredBottle` records can specify preferred bottles.

## Availability Calculation

`availabilityService.ts` computes how many servings a cocktail can make:

- `loadStock()` loads bottles, categories, ingredients and recipes in a fixed number of queries, whatever the number of cocktails
- `computeAvailability()` is pure: volumes come from `Unit.conversionFactorToMl` (`null` = not measured, the line only needs some stock), lines sharing a bottle or a category add up before dividing
- A category counts all its non-empty bottles; `preferredAvailable` only warns when no preferred bottle is left
- An orphan line (known `sourceType` whose source key is NULL or names a missing row, shown "--" in the admin form) stays unavailable with its `reason` and in `missingIngredients`, but does not make the cocktail unavailable. A line with an unknown `sourceType` still does
- The public endpoints add `available` = manual switch (`Cocktail.isAvailable`) and at least one serving in stock
