## Summary

v1.20.0 lets a bar show its public menu in a frame of its own website. Allowed sites are listed in Settings, and the list is empty by default. The images now run on Node 26, the current LTS. At the first start, the backend copies the database to `backups/pre-migrate-<date>.db`, then applies one migration that adds the list of allowed sites. No required action.

## Changes

### Embedding the public menu

- **New setting.** Settings > "Embed the menu in a website" lists the sites allowed to show the public menu in a frame, one address per line, and gives the `<iframe>` code to paste. Addresses must use `https://`; `http://` is accepted only for `localhost` and `127.0.0.1`. The list is empty by default, so nothing changes until you fill it. (#299)
- **What becomes embeddable.** Only the `/menu/…` pages can be framed, and only by the listed sites. The sign-in page, the administration and every other page still refuse any frame. (#299)
- **Backend check.** Each `/menu/` page load asks the backend for the list, with a 3-second limit. If the backend does not answer, the page is still served, but it cannot be framed. (#299)
- **Backups.** The list is part of the database. Restoring a backup brings back the list stored in that backup. A backup made before v1.20.0 brings back an empty list, so the menu cannot be embedded until the sites are entered again. (#299)
- **Database.** One migration, `20261127120000_site_embed_origins`, adds an empty column to the site settings. Before it runs, the backend copies the database to `backups/pre-migrate-<date>.db`, in the `db-data` volume. No existing row changes. (#299)

### Docker and development

- **Node 26.** The backend and frontend images now run on Node 26 (LTS). Development outside Docker needs Node 26 or later (`engines`). (#296)
- **API contracts.** Every JSON route now has a strict response schema checked by the tests, and the frontend types are generated from these schemas. A private field that would leak into a public answer now fails the tests. The answers do not change. (#298, #301)
- **End-to-end tests.** Playwright journeys run against the compose stack on every pull request. (#297)

## Required actions

None. `docker-compose.prod.yml` has not changed since v1.19.0. Pin both images to `:1.20.0`, or `:1.20` to follow the 1.20.x patch releases (`:1.19` does not move to 1.20.0), then pull and restart. At the first start, the backend copies the database to `backups/pre-migrate-<date>.db` and applies one migration (see "Embedding the public menu").

Instances older than v1.12.0: v1.12.0 is a breaking release. Apply its section of [`UPGRADING.md`](https://github.com/Lulu300/carta-cocktail/blob/main/UPGRADING.md#v1120) (and the sections before it) first, check that it works, then apply this one.

**Testing a pre-release**: use `:1.20.0-rc.N` instead of `:1.20.0`.

**If you embed the menu behind a reverse proxy**:
- The proxy must not add its own `X-Frame-Options` header or its own CSP to `/menu/` pages, or the browser refuses the frame.
- A site served over HTTPS can only frame an instance that is also served over HTTPS.

**Rolling back** to v1.19.x: restore the `pre-migrate` copy made at the upgrade, then pin the images back to `:1.19`. Follow [`docs/operations.md`](https://github.com/Lulu300/carta-cocktail/blob/main/docs/operations.md#retour-arrière) ("Retour arrière") or [README › "Restoring a pre-migration backup"](https://github.com/Lulu300/carta-cocktail/blob/main/README.md#restoring-a-pre-migration-backup). What was entered since the upgrade is lost, and the copy brings back its sessions: set a new `JWT_SECRET` afterwards.
