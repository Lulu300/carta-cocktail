## Summary

v1.10.0 makes backup and restore safer: the export holds a consistent copy of the database, and a restore checks the whole archive before it changes anything, keeps a copy of the replaced database and puts everything back if it fails. Cocktail availability is now computed from the conversion factor of each unit, and a cocktail that is switched on but cannot be made (not enough stock, or an ingredient switched off) is greyed out on the public menu and cannot be opened by guests. No required action, but check the size of your latest backup (see "Backups larger than 200 MB").

## Changes

### Backup and restore

- **Confirmation.** Restoring a backup (Settings > Backup & Restore) asks for confirmation in a "Restore Backup" dialog instead of the browser's confirmation box, and shows a success notification when it is done. (#74)
- **Archives refused.** A restore now refuses, before changing anything: (#76)
  - a file larger than 200 MB: `413` "The file or request is too large". The nginx of the frontend image now accepts up to 210 MB on `/api/backup/import` (it accepted 512 MB) and refuses larger files itself, with a `413` too;
  - an archive of more than 500 MB once uncompressed, or of more than 5,000 entries: `400` "Invalid backup file";
  - an archive whose database is corrupt (not a SQLite file, or failing the integrity check) or incomplete (no `User`, `Cocktail`, `Bottle` or `Menu` table), or whose entries cannot be read: `400` "Invalid backup file";
  - a backup made by a newer version of Carta Cocktail: `400` "This backup comes from a newer version of Carta Cocktail: update the application before restoring it".

  Backups exported by earlier versions use the same format, so these limits are the only new reasons for a refusal.
- **Only images restored.** Only the `.jpg`, `.jpeg`, `.png` and `.webp` files of the archive's `uploads/` folder are restored, flat in the photo folder; any other file is skipped, and so is a second image with the same name. The restored photos replace the whole content of the photo folder, sub-folders included (a sub-folder in the photo folder made the restore fail before). (#76)
- **Copy of the replaced database.** Before switching, the restore copies the current database to `backups/pre-restore-<date>.db`, next to the database (`/app/data/backups/` in the `db-data` volume of `docker-compose.prod.yml`). These copies are not deleted automatically: remove the old ones by hand when you no longer need them. (#76)
- **Failed restore.** If the restore fails after the database was replaced, the previous database and photos are put back and the restore answers `500`. Before, a failure could leave a mix of old and restored data. (#76)
- **Backup made before v1.8.0.** It restores, but the database keeps the format of that version until the backend restarts and applies the migrations. Restart the backend after such a restore: `docker compose -f docker-compose.prod.yml restart carta-cocktail-backend`. The admin does not say so yet (later version). A backup from v1.0.x, or from a version older than v1.8.0 with two categories of the same name or two units with the same abbreviation, then stops the backend at startup, as an upgrade from that version would (see the [v1.8.0 and v1.6.0 sections of `UPGRADING.md`](https://github.com/Lulu300/carta-cocktail/blob/main/UPGRADING.md#v180)). To go back to the database you had before the restore, put back its `pre-restore-<date>.db` copy as in [README › "Restoring a pre-migration backup"](https://github.com/Lulu300/carta-cocktail/blob/main/README.md#restoring-a-pre-migration-backup), with `pre-restore-<date>.db` instead of `pre-migrate-<date>.db`. Backups made by v1.8.0 or later need no restart. This is not new in v1.10.0. (#76)
- **API response.** `POST /api/backup/import` now answers `{ message, skippedFiles, restartRecommended }`: `skippedFiles` counts the archive files that were not restored, and `restartRecommended` is `true` for a backup made before v1.8.0. The `success` field is gone: a script that tests it must test the HTTP status (`200`) instead. (#76)
- **Disk space.** The restore no longer works in memory. During a restore, the backend needs free space for the uploaded archive (in the container's `/tmp`), the extracted database and the `pre-restore` copy (next to the database), and the old and new photos side by side (on the photo volume). The export also writes a copy of the database to `/tmp` while it runs. On a nearly full disk, a restore can now fail where v1.9.0 succeeded; nothing is changed in that case. (#76)
- **Export.** The archive holds a consistent copy of the database, taken while the app runs, instead of the live file. `metadata.json` also names the database schema of the backup. If the export fails halfway, the download fails instead of giving a truncated archive. (#76)

### Cocktail availability

- **Units.** Quantities are converted to ml with the conversion factor set on each unit (Admin > Units). Before, the calculation ignored that factor and used a built-in list of abbreviations (`ml`, `cl`, `oz`, `cc`, `cs`, `dash`, `trait`, `cuillère à café`, `cuillère à soupe`, and the piece units `pce`, `piece`, `pièce`, `feuille`, `tranche`, `zeste`, not measured); any other abbreviation counted as 1 ml per unit, whatever its factor. Now: (#75)
  - a unit with a factor uses it. A cup (`tasse`, 250 ml in the default units) now takes 250 ml of the bottle (it took 1 ml), and a hand-made unit such as a 40 ml "shot" now takes 40 ml (it took 1 ml): its servings can drop sharply, and the cocktail can turn grey on the public menu;
  - a unit without a factor is "not measured": the recipe line only needs some stock in the bottle or category. This covers `g`, `rondelle`, `goutte` and the other default units without a factor (they counted 1 ml), and a hand-made unit without a factor, even one in the old list: a hand-made `cl` without a factor counted 10 ml and is now not measured. The admin cocktail list shows ∞ instead of a number of servings when no measured line limits the cocktail. Fill in the unit's factor to count it again.
- **Shared bottles.** Recipe lines that use the same bottle or category add up: two 40 ml lines on a 100 ml bottle make 1 serving, not 2, so servings and availability can change for a recipe that uses the same bottle twice. The low-stock warning lists each bottle or category once. (#75)
- **Public menu.** A cocktail is available to guests when its availability switch is on **and** it can be made: the stock allows at least one serving and every ingredient it uses is switched on. A cocktail that is switched off, short of stock or uses an ingredient switched off is now greyed out, marked "Unavailable" and cannot be opened from the public menu (before, only the switch counted). To show it again, restock the bottle or category, or switch the ingredient on (Admin > Ingredients). The public menu and cocktail API return this as `available`, next to the unchanged `isAvailable`. (#75)
- **Recipe lines without a source.** A recipe line shown as "--" because its bottle, category or ingredient was deleted before v1.8.0 (the v1.9.0 notes said such lines are kept as they are) does not make the cocktail unavailable: the cocktail stays available on the public menu if the rest of the recipe can be made. The admin cocktail list shows its servings instead of "Indisponible", and still lists the line under "❌ Manquant" (these two labels are in French only for now), so you can fix or remove it in the cocktail form. A "--" on a bottle line can also mean that the bottle is empty, since the form only lists bottles that are not empty: that line is not missing its source, and the cocktail stays unavailable until the bottle is restocked. (#78)
- **Speed.** The availability of all cocktails is computed from one load of the stock (7 database queries, whatever the number of cocktails). A bottle menu loads no stock. (#75)

### Backups larger than 200 MB

v1.9.0 accepted backups up to 500 MB; v1.10.0 refuses more than 200 MB, and the export does not warn about that size. Check the size of your latest export (Settings > Backup & Restore): above 200 MB, the app cannot restore it. Photos barely compress, so an instance with many photos can reach that size.

Such a backup can still be restored by hand, with the backend stopped, **only if you made it yourself**: these commands skip the checks of the in-app restore. With `docker-compose.prod.yml`, from its folder (replace `backup-<date>.zip` with your file):

```bash
unzip backup-<date>.zip -d carta-restore
docker compose -f docker-compose.prod.yml stop carta-cocktail-backend
docker compose -f docker-compose.prod.yml run --rm --no-deps -v "$PWD/carta-restore:/restore:ro" \
  --entrypoint sh carta-cocktail-backend -c '
    copy=/app/data/backups/manual-restore-$(date +%Y%m%d-%H%M%S).db
    mkdir -p /app/data/backups
    for f in /app/data/carta_cocktail.db*; do cp "$f" "$copy${f#/app/data/carta_cocktail.db}"; done
    cp /restore/database.db /app/data/carta_cocktail.db
    rm -f /app/data/carta_cocktail.db-wal /app/data/carta_cocktail.db-shm
    if [ -d /restore/uploads ]; then
      find /restore/uploads -maxdepth 1 -type f \( -iname "*.jpg" -o -iname "*.jpeg" -o -iname "*.png" -o -iname "*.webp" \) \
        -exec cp {} /app/uploads/ \;
    fi'
docker compose -f docker-compose.prod.yml up -d
```

The `for` loop keeps a copy of the current database in `/app/data/backups/manual-restore-<date>.db` (with its `-wal` and `-shm` files, if any). Only the `.jpg`, `.jpeg`, `.png` and `.webp` files at the top of the backup's `uploads/` folder are added to the photo folder, as the in-app restore does; sub-folders and other files are skipped, and nothing is copied when the backup has no `uploads/` folder. Photos already in the photo folder are kept, unless the backup has one with the same name. With folders mounted from the host, copy `database.db` (as `carta_cocktail.db`, after removing `carta_cocktail.db-wal` and `carta_cocktail.db-shm`) and the image files at the top of `uploads/` into those folders instead. For a backup made before v1.8.0, the backend applies the migrations at startup, as after an upgrade. Delete `carta-restore` afterwards: it holds a copy of your data.

## Required actions

None. `docker-compose.prod.yml` has not changed since v1.8.0: pin both images to `:1.10.0`, then pull and restart.

Instances older than v1.8.0: apply the section of every version in between first, following [`UPGRADING.md`](https://github.com/Lulu300/carta-cocktail/blob/main/UPGRADING.md), check that it works, then apply this one.

**Testing a pre-release**: use `:1.10.0-rc.N` instead of `:1.10.0`.

Recommended, not required: check the size of your latest backup export (see "Backups larger than 200 MB"), and check the public menu for cocktails that turned grey (see "Public menu").
