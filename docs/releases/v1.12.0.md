## Summary

v1.12.0 runs the backend as the `node` user (uid 1000) instead of root, in an image less than half the size, published for amd64 and arm64. The stack gets health checks, and `docker-compose.prod.yml` no longer publishes the backend port 3001. The admin gets immediate saves in the menu editors, removed bottles on the Apéritifs and Digestifs menus, forced deletion of an item in use, sturdier imports, a full translation and keyboard access. **This is a breaking release**: every existing install must give its data to uid 1000 before upgrading, and anything that calls port 3001 directly must go through nginx. Pin the images to `:1.12.0` instead of `:latest` and follow "Required actions" before pulling.

## Changes

### Docker

- **Non-root backend.** The backend container runs as the `node` user (uid 1000, gid 1000) and never starts as root. Before running anything, the entrypoint checks that it can write to the database folder, `backups/`, the photo folder and its subfolders, and the database files. Otherwise it stops with `ERROR: the backend runs as uid 1000 and cannot write to /app/data.` and the `chown` command to run, and writes nothing. This is what "Required actions" fixes. (#108)
- **Smaller backend image.** The image is built in stages and only ships what runs: production dependencies, the compiled code, the Prisma schema and migrations. About 150 MB compressed, against 320 MB for v1.11.0 (amd64). The packages that the Prisma CLI only uses for `prisma studio` and `prisma dev` are removed, so these two commands no longer work inside the image; the documented commands (`prisma migrate status`, `prisma migrate resolve`, the integrity check) work as before. (#108, #138)
- **New integrity check command.** The old command `--entrypoint npx <image> tsx scripts/check-integrity.ts` no longer works with v1.12.0 and later images (no `tsx`, no sources in the image). The new one, on a copy of the database (not mounted `:ro`: SQLite writes a `-shm` file next to it):

  ```bash
  docker run --rm --user "$(id -u):$(id -g)" -v "$PWD/carta-db-copy:/data" -e DATABASE_URL=file:/data/carta_cocktail.db \
    --entrypoint node ghcr.io/lulu300/carta-cocktail/backend:1.12.0 dist/scripts/check-integrity.js
  ```

  From a checkout (after `npm ci` in `backend/`): `DATABASE_URL=file:/absolute/path/to/copy.db npx tsx src/scripts/check-integrity.ts`. The commands of `UPGRADING.md` that name an older image (v1.8.0 section) stay right for that image. (#108)
- **Commands given to the container.** `docker compose run carta-cocktail-backend <command>` runs the command without the backup, migrations and seed (before: the API started). The README procedures that use `--entrypoint ls`, `--entrypoint sh` or `docker compose exec` now run as `node`; they work unchanged on data owned by uid 1000. (#108)
- **Stop during startup.** A stop request while the backend updates the database lets the running command finish, then exits without starting the next step (exit code 143). (#108)
- **Health endpoint.** `GET /api/health` answers `200 {"status":"ok","version":"1.12.0"}`, or `503 {"status":"unavailable"}` when the database does not answer. It is public through nginx and gives nothing else. (#117)
- **Healthchecks.** Both compose files check the backend (`/api/health`) and the frontend every 30 s, and the frontend waits for a healthy backend. `docker compose up -d --wait` returns once both are healthy. A backend that does not start now keeps the frontend down too: before, nginx served the app with API errors. The frontend check adds a `GET /` line to the nginx access log every 30 s. (#117)
- **Port 3001.** `docker-compose.prod.yml` no longer publishes the backend port: nginx reaches the backend over the compose network, so its headers and limits always apply. `docker-compose.yml` (local build) publishes it on `127.0.0.1` only. See "Required actions". (#117)
- **Multi-arch images.** Both images are published for `linux/amd64` and `linux/arm64`: an arm64 host (Raspberry Pi OS 64-bit, for example) no longer needs to build locally. Both carry an SBOM and a provenance attestation, and know their version (`APP_VERSION`). A release is only published once the full CI of its commit passes. (#118)
- **Version tags.** From this release on, final releases are also tagged `:X.Y` and `:X` (`:1.12` and `:1`), so `:1.12` can follow the 1.12.x patch releases. Pre-releases only get `:X.Y.Z-rc.N`. (#118)
- **Node 24.22.** Both images move from `node:24.21-alpine` to `node:24.22-alpine` (the frontend uses it to build). nginx stays on 1.30. (#142, #143)
- **Quieter startup log.** No more dotenv line, npm update notice or Prisma update box: the lines the release notes point to (backup, migrations, journal mode, port) stand out. The Prisma CLI no longer calls `checkpoint.prisma.io` (`CHECKPOINT_DISABLE=1` in the image). (#126)
- **Prisma 7.10.1.** The backend moves from Prisma 6 to Prisma 7.10.1 with the better-sqlite3 driver, a native module whose prebuilt binaries cover amd64 and arm64. The data format does not change. Query parameters in `DATABASE_URL` (such as `socket_timeout`) are now ignored; the busy timeout is 5 s. (#103, #150)

### Database

- **One migration.** At the first start, the backend copies the database to `backups/pre-migrate-<date>.db` and applies `20261012094739_menu_bottle_exclusion` (a new table for the bottles removed from the system menus). (#99)
- **Failed migration.** When a migration fails, the log now names it, the newest copy made before a migration, and the procedure: [README › "Recovering from a failed migration"](https://github.com/Lulu300/carta-cocktail/blob/main/README.md#recovering-from-a-failed-migration). The backend restores nothing by itself. (#120)
- **Copies before a migration.** After `prisma migrate resolve --rolled-back`, the next start makes a `pre-migrate` copy before running the migration again. While a migration is marked failed, no copy is made, so the newest copy stays the one made before the failed attempt. The two warnings of [UPGRADING › v1.8.0](https://github.com/Lulu300/carta-cocktail/blob/main/UPGRADING.md#v180) (Rolling back) about these points now only apply to the v1.8.0 to v1.11.x images. (#120)
- **Running a previous version.** README has a new section: the current compose file does not fit images of v1.11.x or older (no `/api/health`), and those images run as root. See [README › "Running a previous version"](https://github.com/Lulu300/carta-cocktail/blob/main/README.md#running-a-previous-version). (#120)

### Menus

- **Apéritifs and Digestifs.** These menus hold every bottle checked as aperitif or digestif, **empty ones included**: an emptied, then refilled bottle keeps its place, section and hidden state. The public menu still hides empty bottles. "Synchronize" and the bottle import add every checked bottle; creating or editing a bottle only syncs that bottle. (#99)
- **Removed bottles.** "Remove" on a bottle of a system menu asks for confirmation, then removes it from that menu only: the sync never adds it back, even after the bottle is unchecked and checked again. It stays in the other system menu and available for your own menus. The new "Removed bottles" section lists them, grouped like the menu, and "Put back" returns them at the end of the menu. Deleting the bottle or the menu deletes the exclusion. (#99, #107)
- **Immediate saves.** In both menu editors, every change to the composition (add, remove, visibility, section, order, sections) is saved at once and shown before the server answers. A refused change goes back with a notification; the changes made after it are still saved. Only the menu information (name, slug, description, public) has a "Save" button, and "Cancel" becomes "Back to the list". (#107)
- **System menus** can be renamed: name, description and publication are editable, the slug is read-only. They still cannot be deleted. (#107)
- **Sections** of a bottle menu: create, rename, delete and reorder them in the editor. Moving a group of bottles sends one request. (#100, #107)
- Bottles at 0 % show an "empty" badge in the editor. An unknown menu id shows an error with a link back instead of loading forever. "Synchronize" errors show in a notification. (#107)
- **API.** The type of a menu you created can no longer change (`400`); a bottle can only be added to a bottle menu of its type; a system menu's bottles are managed by the sync and the exclusions. New routes: `POST /api/menu-bottles/menu/:menuId/reorder`, `GET`/`POST /api/menu-bottles/menu/:menuId/exclusions`, `DELETE /api/menu-bottles/menu/:menuId/exclusions/:bottleId`. `POST /api/menu-sections/menu/:menuId/sections/reorder` now needs the full list of sections. A bottle added without a position goes last (it got position 0). (#99, #100)

### Cocktails

- **Cocktail form.** Errors show on the line and block the save: missing source, quantity of 0 or empty, missing unit, blank name. A line already stored with a missing source or a quantity of 0 is kept as it is, with a warning, so an old recipe can still be renamed. Going from a cocktail to "New cocktail" gives an empty form. The unit list has an empty `--` choice. The edit form shows the availability warnings of the saved recipe, including "No preferred bottle available". An emptied description or notes is now saved (it could not be cleared before). A failed photo upload after a creation no longer creates a duplicate on the next save. (#102)
- **Cocktail list.** Deleting asks for confirmation in the app's dialog. A failed batch export shows a notification. (#102)
- **Photos.** Only `.jpg`, `.jpeg`, `.png` and `.webp` files whose type matches their extension are accepted. Uploaded photos get a random file name. A failed upload leaves no file behind, deleting a cocktail deletes its photo, and the previous photo is deleted only once the new one is saved. (#106)
- **Recipe checks.** Saving a recipe line that names a unit, bottle, category or ingredient that no longer exists answers `400` "unknown reference" instead of a bare "Validation error". The form shows the message only, not which line. (#127)

### Import and export

- **Cocktail export.** The admin export and the public one are now the same file, except for notes and preferred bottles, which guests never get. Category lines no longer carry `sourceDetail.desiredStock` (inventory data, not part of a recipe); the import still reads it in older files, and falls back to 1 without it. File names drop accents (`cocktail-pina-colada.json`), and a name without latin letters gives `cocktail-<id>.json`. (#106)
- **ZIP export.** Cocktails with the same name no longer overwrite each other in the archive: they become `cocktail-mojito.json`, `cocktail-mojito-2.json`… The single export button downloads under the same name. (#111)
- **Cocktail import.** A line left without a unit or without a source is refused with the list of every such line, and nothing is written (before, it was saved with a broken unit or no source). A skipped bottle falls back on its category when the category is resolved. Only the units, categories, bottles and ingredients the recipe uses are created. Matches ignore case. Tags written as text (`"a,b"`) are kept. (#127)
- **Cocktail import wizard.** "Try again" retries a failed recipe instead of adding it twice, and the summary has one line per recipe (a skipped recipe counts as not imported). A desired stock of 0 is kept (it became 1), and an emptied number field blocks "Next". Category types are shown in the interface language. Escape closes the wizards; a click outside does not. (#119)
- **Bottle import.** Files saved by Excel in French import: UTF-8 BOM, `;` separator, decimal commas (`25,90`), `VRAI`/`OUI`, line breaks inside quoted fields. Invalid rows are left out and listed in the wizard ("Bottles, line 3: capacityMl is missing") instead of failing the whole import. Limits: 2,000 rows, 2,000 bottles once quantities are counted, and 20 MB per file inside a ZIP. Names are trimmed. A file saved in Windows-1252 still loses its accents. (#113, #119)
- **Bottle import dates.** A date with slashes or dots is read in the order of the interface language: day/month/year in French, month/day/year in English. ISO dates are always accepted. Other formats (`2024`, `March 2024`, `12-03-24`), impossible dates (`31/02/2024`), two-digit years (`03/12/24`) and date + time cells leave their row out as an invalid date instead of being guessed. Exports since v1.3.0 write ISO dates and import as before. (#132)
- **Bottle CSV export.** The file starts with a UTF-8 BOM, so Excel reads its accents. A text cell that starts with `=`, `+`, `-`, `@`, a tab or a carriage return gets a leading `'`, so a spreadsheet does not run it as a formula; the import removes it again. (#113)

### Admin pages

- **Forced deletion.** Deleting a bottle, category or ingredient still in use now offers, after the list of what uses it, a "Delete anyway" button behind an acknowledgment box. The recipes lose the matching lines; deleting a category also deletes its bottles. A notification sums up what changed. Units cannot be forced: the message asks to change the unit of those recipe lines first. (#148)
- **Translations.** The remaining French-only texts are translated (bottle form and tables, units, menus list, availability badges, unit converter), with real plurals. Volumes, degrees and prices follow the language: `0,6 ml`, `40,5 % vol.` and `25,00 €` in French, `1,500 ml` and `€25.00` in English. Still in English in the French interface: the backend's "only N servings left" warning. (#134)
- **Keyboard and screen readers.** Visible focus everywhere, a "Skip to content" link, menus and drop-down lists that open, move with the arrow keys and close with Escape, labelled fields, sortable column headers and pagination as real buttons, ingredient availability as switches, result counts announced, and stronger contrast. Visible changes: an unavailable ingredient only greys its emoji, the restore button is tinted red, and the Login and Settings fields are slightly shorter. (#128)

### Public menu

- **Browsers.** The app now targets Safari and iOS 16.4 or later, Chrome and Edge 111, Firefox 114 (Safari and iOS 16.0 before). Guests on iOS 15, or iOS 16.0 to 16.3, may no longer load the menu. (#105)
- **Lighter first load.** The admin texts are no longer downloaded with the public menu (about 132 kB gzip for the first load, against 138 kB). (#133)
- Keyboard access, skip link and screen reader labels, as in the admin. (#128)

### Security

- `multer` 2.5.0, `zod` 4.6.6 and `body-parser` 2.4.0 fix three high advisories (GHSA-q7qp-rjg7-q26m, GHSA-mrhx-c7xc-m3w5, GHSA-27r3-jxmh-p828, denial of service). A request body compressed with zstd is now decoded; the size limits apply to the decoded body. (#146)
- The advisories of `deepmerge-ts` and `mysql2`, pulled by the Prisma CLI, are fixed by Prisma 7.10.1. The production audit reports no high advisory. (#130, #150)

## Required actions

`breaking: true`. Pin both images to `:1.12.0` (not `:latest`) so that the upgrade only happens once the steps below are done. From this release on, `:1.12` is published too, and follows the 1.12.x patch releases.

Instances older than v1.8.0: apply the section of every version in between first, following [`UPGRADING.md`](https://github.com/Lulu300/carta-cocktail/blob/main/UPGRADING.md), check that it works, then apply this one.

**Testing a pre-release**: use `:1.12.0-rc.N` instead of `:1.12.0`, and `v1.12.0-rc.N` instead of `v1.12.0` in the compose file URL.

### Before upgrading

The backend container now runs as the `node` user (uid 1000, gid 1000) and never starts as root. Earlier images ran as root, so the database and photos of every existing install belong to root.

**Mandatory for every existing install** (#108):

1. Stop the backend: `docker compose -f docker-compose.prod.yml stop carta-cocktail-backend`.
2. Back up the database and the photos:
   - database: README › "Checking a production database before the first upgrade", steps 1 and 2;
   - photos:

     ```bash
     mkdir -p carta-uploads-copy
     docker run --rm --user "$(id -u):$(id -g)" -v <project>_uploads:/uploads:ro -v "$PWD/carta-uploads-copy":/out alpine cp -r /uploads/. /out/
     ```

     With a host folder, copy that folder.
3. Give the data to uid 1000. `<project>` is the folder of the compose file (`docker volume ls | grep db-data` shows the names):
   - **named volumes** (`docker-compose.prod.yml`):

     ```bash
     docker run --rm -v <project>_db-data:/data -v <project>_uploads:/uploads alpine chown -R 1000:1000 /data /uploads
     ```
   - **host folders** mounted on `/app/data` and `/app/uploads` (for example `./data` and `./uploads`):

     ```bash
     docker run --rm -v "$PWD/data":/data -v "$PWD/uploads":/uploads alpine chown -R 1000:1000 /data /uploads
     ```

     or, on the host, `sudo chown -R 1000:1000 data uploads`;
   - **compose file that sets `user:`** for the backend (for example `user: "1026:100"`): run the same command with that uid and gid instead of `1000:1000`;
   - **Docker rootless**: run the alpine command of your case with the rootless Docker. Root in the container changes the owner inside the user namespace. The host then shows a subordinate uid; this is expected. Not tested for this release (no rootless host).
4. **Integrity check** (when the notes ask for it): the old command `--entrypoint npx <image> tsx scripts/check-integrity.ts` no longer works (no `tsx`, no sources in the image). New command, on a copy (not `:ro`: SQLite writes `-shm` next to it):

   ```bash
   docker run --rm --user "$(id -u):$(id -g)" -v "$PWD/carta-db-copy:/data" -e DATABASE_URL=file:/data/carta_cocktail.db \
     --entrypoint node ghcr.io/lulu300/carta-cocktail/backend:1.12.0 dist/scripts/check-integrity.js
   ```

   From a checkout (after `npm ci` in `backend/`): `DATABASE_URL=file:/absolute/path/to/copy.db npx tsx src/scripts/check-integrity.ts`. The commands of `UPGRADING.md` (v1.8.0 section, "Restoring a backup from an older version") stay right for the images they name. For versions that include D-01 (v1.12.0 and later), they need the new command.

**If step 3 is forgotten**, the backend stops at startup (exit code 1, restarted in a loop by `restart: unless-stopped`) and logs `ERROR: the backend runs as uid 1000 and cannot write to /app/data.`, followed by the commands to run. Nothing is written. The same message appears for a folder that belongs to another uid or is mounted read-only. Run step 3, then start again.

5. **Backend port 3001** (#117). With `docker-compose.prod.yml`, the backend API is no longer published on the host port 3001.
   - **Scripts and monitoring** that call `http://<host>:3001/api/...` or `http://<host>:3001/uploads/...`: call `http://<host>:<frontend port>/api/...` / `/uploads/...` instead, through nginx (the frontend service; port 80 by default).
   - **A reverse proxy (SWAG, Traefik…) that targeted port 3001**: point it at the frontend port instead. If `TRUST_PROXY` is a number, add 1: the requests now also go through nginx, and without the extra hop every client shares one login counter, so 10 failures lock everyone out, the admin included, for 15 minutes. The default `TRUST_PROXY` needs no change.
   - **A proxy that reaches `carta-cocktail-backend:3001` over a shared Docker network** is not affected: `expose` changes nothing between containers.
   - **Publishing the port again** in a `docker-compose.override.yml`, bound to the loopback address, only serves processes running on the host itself. A proxy in a container (its `127.0.0.1` is its own) or on another machine cannot reach it and answers 502: point those at the frontend port instead.
     ```yaml
     services:
       carta-cocktail-backend:
         ports:
           - "127.0.0.1:3001:3001"
     ```
   - **A custom compose file** copied from an older `docker-compose.prod.yml`: copy the new `healthcheck` blocks and the `depends_on` condition, and remove the backend `ports` entry (or bind it to `127.0.0.1`).
6. **New compose file.** `docker-compose.prod.yml` changed for the first time since v1.8.0 (step 5). Download it, then put your own changes back in it (ports, volumes, extra variables), and pin both images to `:1.12.0`:

   ```bash
   cp docker-compose.prod.yml docker-compose.prod.yml.bak
   curl -fsSLo docker-compose.prod.yml https://raw.githubusercontent.com/Lulu300/carta-cocktail/v1.12.0/docker-compose.prod.yml
   ```

   ```yaml
   image: ghcr.io/lulu300/carta-cocktail/backend:1.12.0
   image: ghcr.io/lulu300/carta-cocktail/frontend:1.12.0
   ```

   **If you had added `- SQLITE_WAL=false`** to the `environment` list of `carta-cocktail-backend` (database on a network share, see [README › "Database files and network shares"](https://github.com/Lulu300/carta-cocktail/blob/main/README.md#database-files-and-network-shares)), the new file does not have it: add it again, after `- UPLOAD_DIR=/app/uploads`. Otherwise the database goes back to WAL mode, which does not work on SMB or NFS. The same goes for any variable you added there (`TRUST_PROXY`, `LOGIN_RATE_LIMIT`…): the compose files still do not pass them from `.env`.

   ```yaml
         - UPLOAD_DIR=/app/uploads
         - SQLITE_WAL=false
   ```

Then pull and start:

```bash
docker compose -f docker-compose.prod.yml pull
docker compose -f docker-compose.prod.yml up -d --wait
```

### After upgrading

1. `docker compose logs carta-cocktail-backend` shows `API running on port 3001`.
2. Optional: `docker compose exec carta-cocktail-backend ps -o user,args` shows `node` for every process.
3. `docker compose up -d --wait` returns once both services are healthy (or fails if one is not).
4. `docker compose ps` shows `(healthy)` for both services.
5. `curl http://<host>:<frontend port>/api/health` answers `{"status":"ok","version":"…"}`.
6. If the backend fails to start, the frontend is not started either: read `docker compose logs carta-cocktail-backend`, fix the cause, then run `docker compose up -d` again.
7. With `SQLITE_WAL=false`, the startup log shows `SQLite journal mode: delete`.
8. **Check the Apéritifs and Digestifs menus** (#99). "Synchronize", or a bottle import, adds every bottle checked for the menu's type, **empty ones included** (hidden on the public page while empty). Creating or editing a bottle syncs that bottle only. Check both menus and remove, in the menu editor, the bottles that should not be there: a removed bottle stays out of that menu, and the "Removed bottles" section puts it back.

**After restoring a backup made with an earlier version**: restart the backend before using bottles and menus (`docker compose -f docker-compose.prod.yml restart carta-cocktail-backend`). The new table is created by the migrations at the next start; until then, creating, editing or importing bottles, removing a bottle from a menu, the sync and the exclusion routes answer 500. (#99)

### Rolling back

- **Rollback**: after going back to a version before this one (README › "Restoring a pre-migration backup"), which runs as root, run step 3 again before upgrading again. (#108)
- An image older than this release has no `/api/health`: with the new compose file its backend stays `unhealthy` and the frontend never starts. When rolling back to an older image, go back to the previous compose file too (or drop the backend `healthcheck` and the `depends_on` condition). The same applies when using the new compose file with an older tag, or when taking it from `main` before the matching `latest` image is published. (#117)

The full procedure, with the `docker-compose.prod.yml.bak` kept at step 6: [README › "Running a previous version"](https://github.com/Lulu300/carta-cocktail/blob/main/README.md#running-a-previous-version), then [README › "Restoring a pre-migration backup"](https://github.com/Lulu300/carta-cocktail/blob/main/README.md#restoring-a-pre-migration-backup).
