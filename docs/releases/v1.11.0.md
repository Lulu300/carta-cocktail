## Summary

v1.11.0 hardens the admin sign-in: failed logins are limited per IP address, a password change ends the other sessions, and changing the login email asks for the current password. A restore now signs out every session, and the Settings page says when the backend must be restarted and how many files were skipped. The admin pages for units, ingredients, categories, menus and bottles confirm each change with a notification and say why a deletion is refused. No required action, but **restart the backend after restoring a backup made before v1.11.0** (see "Restoring a backup").

## Changes

### Admin sign-in and profile

- **Login limit.** After `LOGIN_RATE_LIMIT` failed logins (10 by default) from one IP address in 15 minutes, the login answers `429` "Too many failed login attempts: try again in a few minutes" for up to 15 minutes. Successful logins do not count. The counters are kept in memory: restarting the backend clears them. (#82)
- **Sign-in errors.** The login page now shows why a sign-in failed: "Invalid email or password" only for wrong credentials, the message above when the login limit is reached, and "Internal server error" for a server error. Before, every failure showed "Invalid email or password". (#91)
- **Behind a reverse proxy.** The API reads the client address from `X-Forwarded-For`, but only from the proxies that the new `TRUST_PROXY` variable trusts. The default (`loopback, linklocal, uniquelocal`) trusts the host and private networks: nginx of the frontend image, and a reverse proxy in front of it on a private Docker network (SWAG, Traefik…), need no setting, and each client gets its own counter. The default has limits, detailed in [README › "Login limit behind a reverse proxy"](https://github.com/Lulu300/carta-cocktail/blob/main/README.md#login-limit-behind-a-reverse-proxy) (#82, #92):
  - A client on your local network can forge its address in `X-Forwarded-For` and get around the limit.
  - With Docker rootless or Podman, Docker Desktop, or IPv6 clients relayed by `docker-proxy` when the Docker daemon has no IPv6, the first proxy sees clients from the Internet under one private address. Clients that do not forge `X-Forwarded-For` already share one counter, so failures from any of them can block the admin for up to 15 minutes, and a client that forges it gets around the limit. In those installs, `TRUST_PROXY=1` (nginx alone) or `TRUST_PROXY=2` (SWAG or another proxy in front of nginx) removes the bypass and adds no risk of blocking the admin. Raise `LOGIN_RATE_LIMIT` if shared-counter blocks happen too often.
  - A client that reaches the backend port 3001 directly, published by the compose files, can also forge its address (with `TRUST_PROXY=1` or `2`, or with the default when it arrives under a private address). So can a client that reaches nginx's port without going through SWAG. Do not publish these ports: remove the `ports` entry of `carta-cocktail-backend` (nginx reaches the backend over the compose network), or bind it to the loopback address (`"127.0.0.1:3001:3001"`). README gives the same for nginx's port behind SWAG.
- **Password change ends the other sessions.** Changing the password in Settings > Admin Profile signs out every other browser and device. The browser that made the change stays signed in. (#82)
- **Login email.** Changing the login email now asks for the current password, as a password change already did, and the email must be a valid address. (#82)
- **12 characters.** A new password must be at least 12 characters long. A shorter password set before this version still works until you change it. (#82)
- **API.** `POST /api/auth/logout-all` (authenticated) signs out every session, the caller's included. The admin has no button for it yet. Changing the password through `PUT /api/settings/profile` returns a new token, since the one that sent the request is no longer valid. (#82)
- **Cross-origin calls.** The API no longer answers other websites (`Access-Control-Allow-Origin: *` before). The app itself does not need it: nginx serves the frontend and the API on the same origin. A tool that calls the API from a browser page on another site needs `CORS_ORIGIN` set to that site's origin. (#82)
- **New optional variables.** `LOGIN_RATE_LIMIT` (default `10`), `TRUST_PROXY` (default `loopback, linklocal, uniquelocal`), `JWT_EXPIRES_IN` (session lifetime, default `7d`, unchanged) and `CORS_ORIGIN` (default empty). The defaults suit a standard install. The backend refuses to start when `LOGIN_RATE_LIMIT`, `TRUST_PROXY` or `JWT_EXPIRES_IN` is set to a value it cannot read. `CORS_ORIGIN` is not checked: a value that does not match the site exactly, with a trailing slash for example, silently allows nothing. The compose files do not pass them from `.env`: to set one in Docker, add it to the `environment` list of `carta-cocktail-backend`, without quotes. See [README › "Environment Variables"](https://github.com/Lulu300/carta-cocktail/blob/main/README.md#environment-variables). (#82, #87)

### Restoring a backup

- **Every restore signs out.** Restoring a backup ends every session, including the one that ran the restore, so that a restore cannot bring back a session revoked by a password change. Sign in again with the admin email and password stored in the backup: a password changed after the backup was made no longer works. If you do not know that password any more, reset it as in [README › "Recovering the admin account"](https://github.com/Lulu300/carta-cocktail/blob/main/README.md#recovering-the-admin-account) (`ADMIN_RESET_PASSWORD`). The restore screen does not say so yet: after the restore, the page leads to the login page. (#93)
- **Sign-out of a backup made before v1.11.0.** Such a backup has no session version yet, so the sign-out happens at the backend restart the restore asks for (see below). The restore writes a `.session-floor` file next to the database (`/app/data/carta_cocktail.db.session-floor` in the `db-data` volume), and the next start applies it and deletes it. If that file cannot be read, the backend refuses to start and its log says what to do: change `JWT_SECRET` (this signs out every session), delete the file, then restart. With `docker-compose.prod.yml`, once the new `JWT_SECRET` is in `.env`:

  ```bash
  docker compose -f docker-compose.prod.yml stop carta-cocktail-backend
  docker compose -f docker-compose.prod.yml run --rm --no-deps --entrypoint rm carta-cocktail-backend /app/data/carta_cocktail.db.session-floor
  docker compose -f docker-compose.prod.yml up -d
  ```

  Without Docker, a start before `npm run db:deploy` stops with a message that asks for it; the file is kept until then. (#93)
- **Restores done by hand.** Putting back a database by hand brings back its sessions, including those revoked since it was made: the README procedure for a backup made before migrations, the manual restore of a backup larger than 200 MB (v1.10.0 notes), or a `pre-migrate-<date>.db` or `pre-restore-<date>.db` copy put back. Afterwards, set a new `JWT_SECRET` in `.env` (`openssl rand -hex 32`) and run `docker compose -f docker-compose.prod.yml up -d`: this signs out every session. (#93)
- **Backups made before v1.11.0.** v1.11.0 adds a column to the `User` table. Restoring any backup made before v1.11.0, v1.8.0 to v1.10.0 included, leaves the database without it until the backend restarts and updates the database. Until then, the admin pages answer with a server error, and so does the public menu in a browser where the admin is signed in. Reloading the page signs you out, and signing in then fails with "Internal server error", even with the right password; these failures count for the login limit, so after 10 attempts the login answers with the limit message until the restart, which clears the counters. Guests are not affected. **Restart the backend after such a restore**: `docker compose -f docker-compose.prod.yml restart carta-cocktail-backend`. A backup from v1.0.x, or from before v1.8.0 with duplicate category names or unit abbreviations, still stops the backend at startup. What to do in each case, with and without Docker: [UPGRADING.md › "Restoring a backup from an older version"](https://github.com/Lulu300/carta-cocktail/blob/main/UPGRADING.md#restoring-a-backup-from-an-older-version). (#82, #88, #91)
- **What the restore screen shows.** When a backup comes from an older database version, Settings > Backup & Restore shows "Restart the backend before going on", with how to do it and the cases where a restart is not enough. It also counts the files of the archive's `uploads/` folder that were not restored (only JPG, PNG and WebP images, once per file name). In both cases the page no longer reloads by itself: a reload button ("Reload the page once the backend has restarted" when a restart is needed) does it once you have read the report and, if needed, restarted the backend. A restore with nothing to report reloads the page as before. (#88)

### Admin pages

- **Units, Ingredients, Categories, Menus and Bottles.** (#83, #84)
  - Creating, updating and deleting an item shows a notification. Deleting asks for confirmation in the app's own dialog instead of the browser's confirmation box. Errors now show in a notification; before, most of them showed nothing on these pages. A second click on "Save" while the first save runs is ignored.
  - While a list loads, the table shows placeholder rows. A loading error shows "Retry" instead of an empty list.
  - A deletion refused because the item is in use names the cocktails and bottles that use it (five names, then "and N more").
  - Menus: a slug already taken shows an error and keeps the form open.
  - Bottles: an export failure shows in a notification. The category column sorts on the category name in the current language.
- **Shortage badge.** Adding, changing or deleting a bottle or a category, or importing bottles, updates the shortage count in the sidebar at once. The admin no longer reloads it on every page change. (#84)
- **Cocktail import.** Closing the cocktail import wizard refreshes the units, categories, bottles and ingredients the import may have created, and the shortage count. Before, those pages could show the old lists for up to 30 seconds. (#86)
- **Category types.** When a type cannot be deleted because categories still use it, the error shows in a notification, in English only for now ("Type is in use by categories"); it was a translated browser alert before. The delete button is already disabled for a type in use, so this only happens when the page is out of date. (#83)
- **Keyboard.** Closing a notification from the keyboard moves the focus back to where it was. (#83)

### Documentation

- README: `SQLITE_WAL` and a new "Database files and network shares" section. While the backend runs, `carta_cocktail.db-wal` and `carta_cocktail.db-shm` sit next to the database: never copy the `.db` file alone, use the backup export or stop the backend first. On a network share (SMB or NFS), set `SQLITE_WAL=false` in the `environment` list of the backend. (#81)

## Required actions

None. `docker-compose.prod.yml` has not changed since v1.8.0: pin both images to `:1.11.0`, then pull and restart. At the first start, the backend copies the database to `backups/pre-migrate-<date>.db` and applies one migration (a new column in the `User` table).

Instances older than v1.8.0: apply the section of every version in between first, following [`UPGRADING.md`](https://github.com/Lulu300/carta-cocktail/blob/main/UPGRADING.md), check that it works, then apply this one.

**Testing a pre-release**: use `:1.11.0-rc.N` instead of `:1.11.0`.

After restoring a backup made before v1.11.0, restart the backend (see "Restoring a backup"). After any restore, sign in again with the password stored in the backup.

Recommended after a database put back by hand (manual restore, `pre-migrate` or `pre-restore` copy): change `JWT_SECRET`, which signs out every session (see "Restores done by hand").

Recommended, not required: do not publish the backend port 3001, and with Docker rootless, Podman, Docker Desktop, or IPv6 clients relayed by `docker-proxy`, set `TRUST_PROXY=1` or `2` to remove the bypass of the login limit (see "Behind a reverse proxy").
