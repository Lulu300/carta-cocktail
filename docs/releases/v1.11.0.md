## Summary

v1.11.0 hardens the admin sign-in: failed logins are limited per IP address, a password change ends the other sessions, and changing the login email asks for the current password. After a restore, the Settings page now says when the backend must be restarted and how many files were skipped. The admin pages for units, ingredients, categories, menus and bottles confirm each change with a notification and say why a deletion is refused. No required action, but **restart the backend after restoring a backup made before v1.11.0** (see "Restoring a backup").

## Changes

### Admin sign-in and profile

- **Login limit.** After `LOGIN_RATE_LIMIT` failed logins (10 by default) from one IP address in 15 minutes, the login answers `429` "Too many failed login attempts: try again in a few minutes" until 15 minutes after the first of these failures. Successful logins do not count. The counters are kept in memory: restarting the backend clears them. The login page still shows "Invalid email or password" for any failure, so an admin blocked by the limit sees that message too. (#82)
- **Behind a reverse proxy.** The API reads the client address from `X-Forwarded-For`, but only from the proxies that the new `TRUST_PROXY` variable trusts. The default (`loopback, linklocal, uniquelocal`) trusts the host and private networks: nginx of the frontend image, and a reverse proxy in front of it on a private Docker network (SWAG, Traefik…), need no setting, and each client gets its own counter. The limit can be bypassed, as in v1.10.0 which had none, by a client that writes a new address in `X-Forwarded-For` at each attempt: (#82)
  - by a client on your local network;
  - by any client, when the first proxy sees clients from the Internet under a private address: Docker rootless or Podman, Docker Desktop, or an IPv6 client relayed by `docker-proxy` when the Docker daemon has no IPv6.

  In those installs, `TRUST_PROXY=1` (nginx alone) or `TRUST_PROXY=2` (SWAG or another proxy in front of nginx) gives one counter shared by all clients: the limit holds, but failures from anyone also block the admin for up to 15 minutes. This only holds while no client can reach the backend port 3001 directly (still published by the compose files), or nginx's port without SWAG: do not forward these ports from the Internet, or block them at the firewall. Details in [README › "Login limit behind a reverse proxy"](https://github.com/Lulu300/carta-cocktail/blob/main/README.md#login-limit-behind-a-reverse-proxy).
- **Password change ends the other sessions.** Changing the password in Settings > Admin Profile signs out every other browser and device. The browser that made the change stays signed in. (#82)
- **Login email.** Changing the login email now asks for the current password, as a password change already did, and the email must be a valid address. (#82)
- **12 characters.** A new password must be at least 12 characters long. A shorter password set before this version still works until you change it. (#82)
- **API.** `POST /api/auth/logout-all` (authenticated) signs out every session, the caller's included. The admin has no button for it yet. Changing the password through `PUT /api/settings/profile` returns a new token, since the one that sent the request is no longer valid. (#82)
- **Cross-origin calls.** The API no longer answers other websites (`Access-Control-Allow-Origin: *` before). The app itself does not need it: nginx serves the frontend and the API on the same origin. A tool that calls the API from a browser page on another site needs `CORS_ORIGIN` set to that site's origin. (#82)
- **New optional variables.** `LOGIN_RATE_LIMIT` (default `10`), `TRUST_PROXY` (default `loopback, linklocal, uniquelocal`), `JWT_EXPIRES_IN` (session lifetime, default `7d`, unchanged) and `CORS_ORIGIN` (default empty). The defaults suit a standard install. The backend refuses to start when one of them is set to a value it cannot read. The compose files do not pass them from `.env`: to set one in Docker, add it to the `environment` list of `carta-cocktail-backend`, without quotes. See [README › "Environment Variables"](https://github.com/Lulu300/carta-cocktail/blob/main/README.md#environment-variables). (#82, #87)

### Restoring a backup

- **Backups made before v1.11.0.** v1.11.0 adds a column to the `User` table. Restoring any backup made before v1.11.0, v1.8.0 to v1.10.0 included, leaves the database without it until the backend restarts and updates the database. Until then, signing in fails (the login page shows "Invalid email or password", even with the right password), the admin pages answer with a server error, and so does the public menu in a browser where the admin is signed in. Guests are not affected. **Restart the backend after such a restore**: `docker compose -f docker-compose.prod.yml restart carta-cocktail-backend`. A backup from v1.0.x, or from before v1.8.0 with duplicate category names or unit abbreviations, still stops the backend at startup. What to do in each case, with and without Docker: [UPGRADING.md › "Restoring a backup from an older version"](https://github.com/Lulu300/carta-cocktail/blob/main/UPGRADING.md#restoring-a-backup-from-an-older-version). (#82, #88)
- **What the restore screen shows.** When a backup comes from an older database version, Settings > Backup & Restore shows "Restart the backend before going on", with how to do it and the cases where a restart is not enough. It also counts the files of the archive's `uploads/` folder that were not restored (only JPG, PNG and WebP images, once per file name). In both cases the page no longer reloads by itself: a "Reload the page" button does it once you have read the report and, if needed, restarted the backend. A restore with nothing to report reloads the page as before. (#88)

### Admin pages

- **Units, Ingredients, Categories, Menus and Bottles.** (#83, #84)
  - Creating, updating and deleting an item shows a notification. Deleting asks for confirmation in the app's own dialog instead of the browser's confirmation box. Errors now show in a notification; before, most of them showed nothing on these pages. A second click on "Save" while the first save runs is ignored.
  - While a list loads, the table shows placeholder rows. A loading error shows "Retry" instead of an empty list.
  - A deletion refused because the item is in use names the cocktails and bottles that use it (five names, then "and N more").
  - Menus: a slug already taken shows an error and keeps the form open.
  - Bottles: an export failure shows in a notification. The category column sorts on the category name in the current language.
- **Shortage badge.** Adding, changing or deleting a bottle or a category, or importing bottles, updates the shortage count in the sidebar at once. The admin no longer reloads it on every page change. (#84)
- **Cocktail import.** Closing the cocktail import wizard refreshes the units, categories, bottles and ingredients the import may have created, and the shortage count. Before, those pages could show the old lists for up to 30 seconds. (#86)
- **Category types.** When a type cannot be deleted because categories still use it, the error shows in a notification, in English only for now ("Type is in use by categories"); it was a translated browser alert before. The delete button is already disabled for a type in use, so this only happens when the page is out of date. (#83)
- **Keyboard.** Closing a notification from the keyboard moves the focus back to where it was. (#83)

### Documentation

- README: `SQLITE_WAL` and a new "Database files and network shares" section. While the backend runs, `carta_cocktail.db-wal` and `carta_cocktail.db-shm` sit next to the database: never copy the `.db` file alone, use the backup export or stop the backend first. On a network share (SMB or NFS), set `SQLITE_WAL=false` in the `environment` list of the backend. (#81)

## Required actions

None. `docker-compose.prod.yml` has not changed since v1.8.0: pin both images to `:1.11.0`, then pull and restart. At the first start, the backend copies the database to `backups/pre-migrate-<date>.db` and applies one migration (a new column in the `User` table).

Instances older than v1.8.0: apply the section of every version in between first, following [`UPGRADING.md`](https://github.com/Lulu300/carta-cocktail/blob/main/UPGRADING.md), check that it works, then apply this one.

**Testing a pre-release**: use `:1.11.0-rc.N` instead of `:1.11.0`.

After restoring a backup made before v1.11.0, restart the backend (see "Restoring a backup").

Recommended, not required: with Docker rootless, Podman, Docker Desktop, or IPv6 clients relayed by `docker-proxy`, set `TRUST_PROXY` as described in "Behind a reverse proxy".
