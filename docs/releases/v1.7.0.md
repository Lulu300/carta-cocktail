## Summary

v1.7.0 moves the images to Node 24 LTS and gives the API proper error answers: a wrong id, a malformed request or a file that is too large now gets a translated JSON error with the right HTTP status, instead of a generic 500 or an HTML page. No action is needed when you use the published images: pin them to `:1.7.0` and upgrade.

## Changes

### Docker

- **Node 24 LTS.** The backend image and the build stage of the frontend image now use `node:24.21-alpine` instead of `node:20-alpine`. Node 20 reached its end of life on 2026-04-30 and no longer gets security fixes. Ports, variables, volumes and the entrypoint are unchanged. (#53)
- `node:24-alpine` is published for amd64, arm64 and s390x only. Building the images yourself on a 32-bit ARM host (armv6/armv7) no longer works; the published images (amd64) are not affected. (#53)

### API

- **One error handler for the whole API.** Error answers keep the `{ "error": "..." }` shape, translated from `Accept-Language`, and never contain a stack trace. Some errors now carry an optional `details` field. Cases that used to answer `500` now get a client status (#54):
  - `400` for an id that is not a number (`/api/units/abc`), a field type the database rejects, a reference to a row that does not exist (an unknown unit in a cocktail, for example), a malformed JSON body, or an unexpected upload field;
  - `404` for an unknown id on update or delete, and for an unknown `/api/...` path (JSON instead of the HTML page of the web server);
  - `409` when deleting a row that is still in use (a unit used by a cocktail, a preferred bottle…) or when creating a duplicate;
  - `413` for an image or a backup file over the size limit, and for a JSON body over the limit (JSON instead of an HTML page).
- A bottle import file that cannot be read answers `400` "The import file could not be read", with the parser message in `details.reason`. (#54)
- Answers that already had the right status, such as the `401` of a failed login, are unchanged. (#54)

### Development

- Node 24 is required to work on the project (`.nvmrc`, `engines: ">=24"` in both packages). (#53)
- Coverage is measured on every source file, including files no test imports, and the 80 % check on changed lines now counts a line only when code that starts on it ran. Frontend thresholds follow a ratchet (branches and functions at 54 %, never lowered, raised back to 60 % by later work). (#52)
- First building blocks of the admin design system: theme colour tokens and base components (`Button`, `Modal`, `Field`…). No page uses them yet, so nothing changes on screen. (#51)
- An upgrade test bench (`scripts/upgrade-test/`) replays upgrades on a copy of a real database before each final release. (#46)

## Required actions

None when you use the published images. Pin both images to `:1.7.0` in `docker-compose.prod.yml` (`:1.7.0-rc.N` to test a pre-release), then pull and restart:

```bash
docker compose -f docker-compose.prod.yml pull
docker compose -f docker-compose.prod.yml up -d
```

Instances older than v1.6.0 must first apply the sections of the versions they skip in [`UPGRADING.md`](https://github.com/Lulu300/carta-cocktail/blob/main/UPGRADING.md), from the oldest to the newest.

### Before upgrading

1. **Only if you build the images yourself on a 32-bit ARM host** (`docker compose up --build` on armv6/armv7, such as Raspberry Pi OS 32-bit or some ARM NAS models): the build now stops at `FROM node:24.21-alpine` with `no matching manifest`. Build on a 64-bit host (amd64 or arm64) instead, or use the published images. `uname -m` prints `armv6l` or `armv7l` on a 32-bit ARM host.
