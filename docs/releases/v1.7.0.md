## Summary

v1.7.0 moves the images to Node 24 LTS and gives the API proper error answers: a wrong id, a malformed request or a file that is too large now gets a translated JSON error with the right HTTP status, instead of a generic 500 or an HTML error page. No action is needed with the published images: pin them to `:1.7.0` and upgrade. **v1.7.0 does not run on 32-bit ARM hosts** (armv6/armv7); see "Required actions".

## Changes

### Docker

- **Node 24 LTS.** The backend image and the build stage of the frontend image now use `node:24.21-alpine` instead of `node:20-alpine`. Node 20 reached its end of life on 2026-04-30 and no longer gets security fixes. Ports, variables, volumes and the entrypoint are unchanged. (#53)
- **32-bit ARM is no longer supported.** `node:24-alpine` is published for amd64, arm64 and s390x only, and the published Carta Cocktail images are amd64 only. An instance built on a 32-bit ARM host (armv6/armv7) cannot be built or run with v1.7.0; it stays on v1.6.0 or moves to a 64-bit system. (#53)

### API

- **One error handler for the whole API.** Error answers keep the `{ "error": "..." }` shape, translated from `Accept-Language`, and never contain a stack trace. An optional `details` field is added (used by the bottle import error below). Cases that used to answer 500, or Express's HTML error page, now get a JSON answer with a client status (#54):
  - `400` for an id that is not a number (`/api/units/abc`), a field type the database rejects, a reference to a row that does not exist (an unknown unit in a cocktail, for example), a malformed JSON body, or an unexpected upload field;
  - `404` for an unknown id on update or delete, and for an unknown `/api/...` path (JSON instead of Express's HTML page);
  - `409` when deleting a row that is still in use (a unit used by a cocktail, a preferred bottle…); duplicates now answer `409` on every route (several already did);
  - `413` for an image, a backup file or a bottle import file over the size limit, and for a JSON body over the limit (JSON instead of an HTML page).
- A bottle import file that cannot be read answers `400` "The import file could not be read", with the parser message in `details.reason`. (#54)
- Answers that already had the right status, such as the `401` of a failed login, are unchanged. (#54)
- Backend logs now record only server errors (5xx); client errors (400, 404, 409, 413) are no longer logged. (#54)

### Development

- Node 24 is required to work on the project (`.nvmrc`, `engines: ">=24"` in both packages). (#53)
- Coverage is measured on every source file, including files no test imports, and the 80% check on changed lines now counts a line only when code that starts on it ran. Frontend thresholds follow a ratchet (branches and functions at 54%, never lowered, raised back to 60% by later work). (#52)
- First building blocks of the admin design system: theme colour tokens and base components (`Button`, `Modal`, `Field`…). No page uses them yet, so nothing changes on screen. (#51)
- An upgrade test bench (`scripts/upgrade-test/`) replays upgrades on a copy of a real database before each final release. (#46)

## Required actions

None with the published images. `docker-compose.prod.yml` has not changed since v1.5.0: only the image tags change. Pin both images to `:1.7.0` (`:1.7.0-rc.N` to test a pre-release), then pull and restart:

```bash
docker compose -f docker-compose.prod.yml pull
docker compose -f docker-compose.prod.yml up -d
```

Instances older than v1.6.0: upgrade to v1.6.0 first, following its section of [`UPGRADING.md`](https://github.com/Lulu300/carta-cocktail/blob/main/UPGRADING.md#v160), check that it works, then apply this one.

### Before upgrading

1. **Only on a 32-bit ARM host.** Check the architecture Docker runs with:

   ```bash
   docker version --format '{{.Server.Arch}}'
   ```

   If it prints `arm` (armv6/armv7, for example Raspberry Pi OS 32-bit, even on a Raspberry Pi 4 or 5 where `uname -m` prints `aarch64`): v1.7.0 does not run on 32-bit ARM. The `node:24-alpine` base image cannot be pulled for this platform, so the build stops (`no match for platform in manifest`, or `no matching manifest for linux/arm/v7` with the legacy builder), and the published images are amd64 only. Stay on v1.6.0, or move the instance to a 64-bit system (amd64, or arm64, for example Raspberry Pi OS 64-bit on a Raspberry Pi 3 or newer) and build there. The build fails before any container is replaced, so the running v1.6.0 instance keeps working.
