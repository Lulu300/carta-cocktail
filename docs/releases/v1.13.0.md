## Summary

v1.13.0 limits the number of API requests per client IP address (per /64 network for IPv6), with a stricter limit on backup export and import. The admin stays signed in when the session check fails for another reason than an expired session, and the cocktail export and the menu bottle editor send fewer requests. A page that fails to display now shows an error screen with a way out instead of a blank page, the last backend messages that were only in English are translated, and the backend log no longer repeats the value of `ADMIN_RESET_PASSWORD`. No required action: `docker-compose.prod.yml` and the database do not change.

## Changes

### API rate limits

- **Every API request counts.** Each client IP address (each /64 network for IPv6) may send `API_RATE_LIMIT` requests to the API in one minute (600 by default). Beyond that, the API answers `429` "Too many requests: try again in a few minutes" (in French, "Trop de requêtes : réessayez dans quelques minutes"), with a `Retry-After` header, until the minute is over. Public menu, admin pages and sign-in all count, with or without a session. `/api/health` (the Docker healthcheck) and the photos (`/uploads`) do not. A request over the limit is refused before its body is read. (#169)
- **Backup export and import.** On top of the limit above, Settings > Backup & Restore allows 10 exports and imports together per 15 minutes from the admin's address; the 11th shows the same "Too many requests" message. Only requests with a valid session count, so other clients cannot use up this limit. (#169)
- **Shared addresses.** The limits count per client IP address (per /64 network for IPv6): clients that share one, such as guests behind a bar's Internet connection, a NAT or a proxy, share the 600 requests per minute. In the installs where every client from the Internet reaches the API under one private address (Docker rootless or Podman, Docker Desktop, IPv6 clients relayed by `docker-proxy`), they all share one count. If guests get "Too many requests", raise `API_RATE_LIMIT`. `TRUST_PROXY` decides which address counts, as for the login limit: see [README › "Login limit behind a reverse proxy"](https://github.com/Lulu300/carta-cocktail/blob/main/README.md#login-limit-behind-a-reverse-proxy), which now covers the three limits. (#169)
- **IPv6 clients.** The rate limits count an IPv6 client for its /64 network (one LAN). The login limit counted per /56 in v1.11 and v1.12. Devices on the same Wi-Fi share a counter; other networks of the same site (a guest network and a staff network) and mobile subscribers each get their own. Only installs where the API sees real IPv6 client addresses (a reverse proxy or tunnel that receives IPv6) notice the change. (#179)
- **What the app shows.** The login page and Settings > Backup & Restore show the message of the `429`, and so does the notification of an admin action that fails. A list or a public menu page that fails to load shows its usual loading error with "Retry". (#169)
- **The admin stays signed in.** When the app loads, it checks the stored session. Before, any failure of that check signed the admin out, so a `429` sent them to a login page that answered `429` too. Now only a `401` (expired or revoked session) goes back to the login page. After a `429`, a server error or a network error, the admin stays signed in:
  - on an admin page, they see "Your session could not be checked" with the server message (or "Check your connection and try again." after a network error), a "Retry" button, a "Sign in again" button (ends the session and opens the login page, which returns to the requested page afterwards) and a "Back to home" link;
  - on a public page, they see the guest header and footer for that load. Reloading the page once the limit has passed brings the admin header back, without signing in again. (#175)
- **The bar's name and icon come back.** After a refused ("Too many requests") or failed (network error, backend restarting) load, the public menu and the admin pages showed "Carta Cocktail" and the default icon for the rest of the visit. They now get the bar's name and icon back in the header and the tab without a reload: after the delay the server asks for (or 30 seconds), up to three times, or when the guest clicks "Retry". (#176)
- **Cocktail ZIP export.** Exporting several cocktails as a ZIP sends one request per 500 cocktails instead of one per cocktail, so it no longer reaches the limit. API: `POST /api/cocktails/export` with `{ "ids": [...] }` (1 to 500 ids) returns `[{ filename, data }]` in the order of the ids, the same files as `GET /api/cocktails/:id/export`; an unknown id answers `404` for the whole batch. (#177)
- **Menu bottle editor.** Hiding, showing, moving to a section or putting back a group of bottles sends one request, whatever the number of bottles, so these actions no longer reach the limit. A refused group action now leaves the whole group unchanged; before, the part already accepted stayed applied. API: `PUT /api/menu-bottles/menu/:menuId/entries` (`{ ids, isHidden?, menuSectionId? }`) and `POST /api/menu-bottles/menu/:menuId/exclusions/restore` (`{ bottleIds }`), each all or nothing. (#178)
- **New optional variable `API_RATE_LIMIT`** (default `600`): a positive integer. Any other non-empty value stops the backend at startup with `API_RATE_LIMIT must be a positive integer, got '<value>'`. Like `LOGIN_RATE_LIMIT` and `TRUST_PROXY`, the compose files do not pass it from `.env`: to change it in Docker, add it to the `environment` list of `carta-cocktail-backend`, without quotes. The counters are kept in memory: restarting the backend clears them. The backup limit is fixed. See [README › "Environment Variables"](https://github.com/Lulu300/carta-cocktail/blob/main/README.md#environment-variables). (#169)

### Error screen

- **No more blank page.** When a page cannot be displayed, the app shows "This page could not be displayed" ("Impossible d'afficher cette page"), with "Reload" and "Back to home", instead of a blank page. This covers an admin page or the login page whose file is still missing after the automatic reload (a tab opened before an upgrade, or a lost connection), and any page, public or admin, that fails while rendering. Going to another page clears the error without reloading. (#165)

### Translations

- **Backend messages.** The last English-only messages of the backend are translated: creating a category type that already exists, deleting a type still used by categories (the delete button is already disabled for a type in use, so this only shows when the page is out of date), and an unknown type. Still in English in the French interface, as in v1.12.0: the backend's "only N servings left" warning. (#166)
- **API.** For clients that call the API directly; the app does not depend on these changes. Deleting a category type still used by categories answers `409` instead of `400`. The `401` answers follow the request language: a request with an expired or revoked token answers "Your session has expired or is no longer valid: sign in again" (it was `Invalid token`), and a request without a token "Unauthorized" ("Non autorisé" in French; it was always in English). The success messages of category types and menu sections are translated. `POST /api/ingredients/bulk-availability` answers `{ message, updated }` instead of `{ updated }`. (#166)

### Logs

- **`ADMIN_RESET_PASSWORD`.** For a value other than `true`, `false` or empty, the startup warning no longer repeats the value. It now says `ADMIN_RESET_PASSWORD is ignored: only the exact value 'true' resets the admin credentials (values such as 'TRUE' or '1' do not)`. Older versions wrote the value to the backend log: if you ever put a password there, consider it exposed wherever those logs were kept. The reset itself has not changed: only `true` resets the admin email and password. (#168)

### Security

- The production dependencies of the backend image have no known advisory left (`npm audit --omit=dev`; there were 5 moderate): `ip-address` 10.7.6, used by the rate limits, and `minimatch` 11 under `archiver`, which the backup export loads. (#164)

## Required actions

None. `docker-compose.prod.yml` has not changed since v1.12.0: pin both images to `:1.13.0` (or `:1.13` to follow the 1.13.x patch releases; `:1.12` does not move to 1.13.0), then pull and restart. No migration: the backend makes no `pre-migrate` copy and the database does not change.

Instances older than v1.12.0: v1.12.0 is a breaking release. Apply its section of [`UPGRADING.md`](https://github.com/Lulu300/carta-cocktail/blob/main/UPGRADING.md#v1120) (and the sections before it) first, check that it works, then apply this one.

**Testing a pre-release**: use `:1.13.0-rc.N` instead of `:1.13.0`.

**If you download `docker-compose.prod.yml` again** (not needed for this release), put back the lines you added to the `environment` list of `carta-cocktail-backend`: the file does not have them. In particular `- SQLITE_WAL=false` (database on a network share, see [README › "Database files and network shares"](https://github.com/Lulu300/carta-cocktail/blob/main/README.md#database-files-and-network-shares)), after `- UPLOAD_DIR=/app/uploads`, otherwise the database goes back to WAL mode, which does not work on SMB or NFS. The same goes for `API_RATE_LIMIT`, `LOGIN_RATE_LIMIT`, `TRUST_PROXY` and the other variables you added there.
