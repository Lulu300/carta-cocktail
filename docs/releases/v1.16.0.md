## Summary

v1.16.0 adds personal aperitif and digestif menus, and makes the bottle and cocktail imports much safer. Imports no longer lose rows because of a misplaced CSV quote. They reuse a category or unit that already exists, ignoring case and accents typed differently, instead of creating a duplicate. They flag a problem before you click "Confirm import", not after. It fixes a security advisory in a translation library (GHSA-mjcw-gfh6-3cxm). The backend no longer sends HSTS: if you rely on it, enable it in your reverse proxy. The compose files now read the optional backend settings, `SQLITE_WAL` included, from `.env`. No migration, no required action.

## Changes

### Menus

- **Personal aperitif and digestif menus.** A new menu can now be an Aperitifs or Digestifs menu, besides a Cocktails menu. The type is chosen at creation and cannot be changed afterwards. A personal menu is filled by hand from the bottles checked for its type. "Add" adds every identical bottle of a group at once. The public page `/menu/<slug>` shows it like the system menus, with empty bottles hidden. (#227)
- **After creating a menu**, its editor opens, for cocktail menus too, instead of staying on the list. (#227)
- **System menus** "Aperitifs" and "Digestifs" stay automatic. In their "Removed bottles", a bottle that is no longer checked for the type is now marked: "Put back" only takes it off that list. "Put back" no longer shows such a bottle in the menu for a moment. (#227)
- **API.** For clients that call the API directly: two group routes are new, `POST /api/menu-bottles/menu/:menuId/entries` and `POST /api/menu-bottles/menu/:menuId/entries/remove`. The id lists of the group routes are now capped at 500 ids (400 above). (#227)

### Bottle import

- **CSV quotes.** A quote inside a cell (`Bourbon 12" edition`) is read as text and no longer makes the following rows disappear. A row with malformed quotes, such as an opening quote never closed or text after a closing quote (`"Special" Reserve`), is listed among the rows set aside in the preview, with its line and column. The rows after it are read. A valid CSV, from the app's export or from Excel, imports exactly as before. (#225)
- **Malformed header.** A file whose header line has a misplaced quote is refused with a message that names it (`bottles.csv` or `categories.csv`). A ZIP whose `categories.csv` is in this case is therefore refused as a whole; before, its categories were ignored without a message. (#225)
- **Values on several lines.** A value on several lines in a single-line field (name, category, type, location, category name or translation) shows in the preview under "values to check", with its line and field. A misplaced quote can join several lines of the file into one name. The warning does not block the import, and the value is imported as it is. (#237)
- **Rows and categories.**
  - The wizard shows, for each bottle, the category the import puts it in. Before, it showed "Pick a category" when the file wrote the name with another case (`rhum` for `Rhum`), and the file's name when the category was created under another name.
  - A bottle can be put in any existing category. "will be created" marks only the categories the import really creates, under the name they get.
  - The bottles of a category created under another name now go in that category, instead of being skipped or put in the existing category of the file's name.
  - Only the bottles already in the category a row goes in count as duplicates.

  (#228, #229, #236)
- **JSON files.** A JSON bottle file whose rows name a category its category list leaves out now gets that category, with the default values, as a CSV file does. Its bottles are imported instead of skipped. (#228)

### Cocktail import

- **Refusal details.** When the import of a cocktail is refused because a unit, a category, a bottle or an ingredient is neither matched nor created, the error lists each one with its line and name. When a saved cocktail points to an item deleted in the meantime, the message names the line and the field. (#235)
- **Ingredients.** The import uses the ingredient that already holds a name, also when it was typed with decomposed accents, or when the file names it in both forms. Before, it failed with "This entry already exists". (#230)

### Both imports: existing categories, units and types

- **Case.** An import that creates a category or a unit that already exists, ignoring case, now uses the existing one as it is. Its type, stock and translations are kept, whatever the wizard said, and the wizard says so next to the name; the confirmation summary counts it as used, not created. Before, the import created a duplicate or failed with "This entry already exists". (#226, #228)
- **Several matches.** Older data can hold several categories or units that differ only by case. When the file matches none of them exactly, the wizards now show "Several matches" with their names, and keep the import disabled until one is picked or the entry is created under another name. (#226, #228)
- **Category type picked.** A category created by an import goes under the existing type picked in the wizard, spaces included, as a category created by hand does. (#216)
- **Empty type.** The wizards flag a category to create under the type with an empty name (data older than v1.9.0), or under a new type made only of spaces or invisible characters, and keep the import disabled until another type is chosen. The bottle wizard says above its list how many categories need another type. Before, the import failed at the confirmation. (#221)
- **Startup.** The startup seed no longer recreates a default unit (`cl`) that was renamed in another case (`CL`). (#226)

### Names: case, spaces, invisible characters, accents

- **Accents typed differently.** A name pasted with decomposed accents (often copied from macOS file names) looks the same as the usual one but was stored differently. New or edited names of categories, units, ingredients and category types, and their translations, are now stored in the usual composed form (NFC).
  - A category name or unit abbreviation is refused next to the same name written the other way (409), as `rum` already was next to `Rum`. An ingredient name is refused in the same case.
  - A new category type joins the existing one.
  - Existing names stay unchanged until you edit them.

  (#222, #230)
- **Marked names on every admin screen.** The categories table, Shortages, the bottle form and the import wizards now mark category type names the way Manage Types already did. The marked names are: names with spaces around them, repeated or tabs (`␣`, "(with spaces)"); empty names ("(no name)"); names with invisible characters (`[U+200B]`, "(with invisible characters)"); names not in the composed form ("(non-standard Unicode form)"). Nothing is marked on the public pages. (#212, #218, #222)
- **Invisible characters.** A new category type loses its invisible characters (zero-width space, direction marks…), except the joiners that some scripts and emoji need. U+2800, U+3164 and U+FFA0 count as spaces. (#218)
- **Integrity check.** `check-integrity` now also reports, as blocking, category names or unit abbreviations that differ only by the case of an accented letter (`Écorce` and `écorce`) or by Unicode form. It used to miss them. Such a category or unit cannot be edited until one of the pair is renamed (409). (#230)

### Backup and restore

- **Signing out.** Before a restore, the confirmation says that you will have to sign in again with the email and password of the backup. After the restore, the sign-in page opens and says it again. The restore report's button is now "Sign in again once the backend has restarted". (#223)

### Docker and configuration

- **Settings from `.env`.** Both compose files now pass the optional backend variables `SQLITE_WAL`, `JWT_EXPIRES_IN`, `LOGIN_RATE_LIMIT`, `API_RATE_LIMIT`, `TRUST_PROXY` and `CORS_ORIGIN` from `.env`. When they are unset or empty, the backend keeps its defaults.
  - A value already in your `.env`, which Docker ignored until now, starts to apply when you use the new compose file.
  - An existing compose file, with lines you added by hand, keeps working.

  See "Required actions" if you download the new file. (#224)
- **Frontend healthcheck.** The frontend image now answers `/healthz`, which is kept out of the access log (`docker compose logs` of the frontend), and the new compose files probe it instead of `/`. That is about 2,900 fewer lines a day, and visitors' requests stay in the log. The probe is set in the compose file: a current file keeps probing `/`, which still works and stays in the log. (#234)
- **Backend image.** Test and restore leftovers are kept out of the image. (#233)

### Security

- **i18next-http-middleware 3.11.1** fixes GHSA-mjcw-gfh6-3cxm (CVE-2026-132267). Unauthenticated requests with made-up languages (`?lng=`, cookie, `Accept-Language`) made an in-memory list grow without limit until the next restart. The API now serves only `en`, `en-GB` and `fr`; any other language gets English, number formats included. (#213)
  - For API clients whose first language is not supported, import dates now follow the language of the messages. With `Accept-Language: de-DE, fr;q=0.5`, `12/03/2024` is read as 12 March (French, day first), no longer as 3 December. The app always sends `fr`, `en` or `en-GB` and is not affected.
- **HSTS.** The backend's answers (`/api/*`, `/uploads/*`) no longer carry `Strict-Transport-Security`. Before, helmet sent it for one year, subdomains included, so a site served over HTTPS had HSTS on the whole host and its subdomains through these answers.
  - To keep HSTS, enable it in your reverse proxy (Caddy example in [`docs/operations.md`](https://github.com/Lulu300/carta-cocktail/blob/main/docs/operations.md#https) › HTTPS) or with the commented line of `frontend/security-headers.conf`.
  - Browsers that saved the old header keep it until it expires (one year), so a subdomain served over plain HTTP stays forced to HTTPS until then.

  (#211)

### Documentation

- `docs/operations.md` now says that 200 MB is the backend's restore limit; nginx accepts up to 210 MB. A file of exactly a documented upload limit is accepted, as before, and this is now tested. (#214)

## Required actions

None. No migration. Pin both images to `:1.16.0`, or `:1.16` to follow the 1.16.x patch releases (`:1.15` does not move to 1.16.0), then pull and restart.

Instances older than v1.12.0: v1.12.0 is a breaking release. Apply its section of [`UPGRADING.md`](https://github.com/Lulu300/carta-cocktail/blob/main/UPGRADING.md#v1120) (and the sections before it) first, check that it works, then apply this one.

**Testing a pre-release**: use `:1.16.0-rc.N` instead of `:1.16.0`.

**If your site relies on HSTS** (served over HTTPS without a reverse proxy that sends it), enable it in the reverse proxy or with the commented line of `frontend/security-headers.conf` (see "Security").

**If you download `docker-compose.prod.yml` again** (optional for this release): the new file passes `SQLITE_WAL` and the other optional backend variables from `.env`, and its frontend healthcheck probes `/healthz`, which keeps the probes out of the access log.

- Put in `.env` the variables you had added by hand to the `environment` list of `carta-cocktail-backend`, such as `SQLITE_WAL=false` on a network share (see [README › "Database files and network shares"](https://github.com/Lulu300/carta-cocktail/blob/main/README.md#database-files-and-network-shares)).
- If you put such a line back in the new file instead, keep it at the end of the `environment` list. Otherwise the empty entry below it wins, and the variable goes back to its default without a warning.
- If your installation reads these variables from an `env_file`, move them to `.env` or remove their lines from the new file, for the same reason.
- A value already in `.env`, which Docker ignored until now, starts to apply. Check these values before you restart: the backend refuses to start with a value it cannot read (`JWT_EXPIRES_IN`, `LOGIN_RATE_LIMIT`, `API_RATE_LIMIT`, `TRUST_PROXY`), as outside Docker.

Keep your current file and nothing changes.

**Rolling back** to v1.15.x: pin the images back to `:1.15`. There is no migration, so the database needs no restore.
